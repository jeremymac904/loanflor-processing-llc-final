## Findings and follow-ups

1. **Upload endpoint is unauthenticated by design** (public LO form, no accounts). Mitigations: per-submission scoping, no listing across submissions, rate limit, validation, and the fact that uploaded objects are never served back publicly. If the owner wants stronger control, the cheapest step is a per-submission upload token minted by `POST /api/loan-submissions/start` — not built, not required by the brief.
2. **No antivirus scan.** Magic-byte and script checks stop the cheap attacks; a real scan (ClamAV on the API host, or Supabase's edge scanning) is a production follow-up before real borrower files. Flo never executes documents; Ashley's **Open** hands the file to her OS viewer.
3. **Supabase production credentials** are the single outstanding secret: service-role key on the API host only. Never put it in the website build, the Flo repo, or Hermes logs.
4. **`PUBLIC_API_BASE_URL` must be the private/tunnel-reachable base** Flo can call; if it points at a host Flo cannot reach, every document lands as *Needs review* with `checks.fetch_failed` and Malcolm/Flo can retry with `flo_documents action=refetch` once fixed (verified in tests).
5. **Ashley's preview** reads the private copy through the existing Electron preload (`readFileDataUrl`), which already enforces the app's data-URL size cap and path rules; a 25 MB PDF is over the default preview cap and falls back to **Open**.
6. **Website document records after delivery** stay on the API host as the audit trail; the cleanup job in `DOCUMENT_STORAGE_SCHEMA.md` is documented, not built.
