## Mobile upload flow

In the in-app browser at a 375 × 812 viewport (`?lfDemo=1&lfStep=documents`, Vite dev with `/api` proxied to the real API): the Documents step lays out single-column (category select, type select, drop zone, list), and three synthetic files dropped on the zone from the page went through the real `PUT` endpoint — `mobile_1003.pdf` → **Received**, the same bytes under `mobile_1003 copy.pdf` → **Duplicate — already have this one**, `acct_123456789012.pdf` → **failed with the server's message and a Retry button**. Each row shows filename, category, size and status. A native file picker / camera capture was not driven (the sandboxed browser cannot open one); the `<input type="file" multiple accept=".pdf,.jpg,.jpeg,.png">` is what a phone uses.

## Not covered / honest limits

* Production storage (Supabase private bucket) was exercised only against a fake Storage API in unit tests; the end-to-end run used the local-disk driver. Pointing it at a real project needs the owner's decision and key (see `DOCUMENT_UPLOAD_IMPLEMENTATION.md`).
* No OCR: an image or a scanned PDF without a text layer is stored and shown as *Needs review*, not read.
* The browser Documents step (per-file uploads, Retry, Remove, subtype/borrower selects, confirmation with "Documents received" and `LF-…`) was verified by typecheck + production build and by exercising the same endpoints it calls from the driver script; a mouse-driven browser pass was not repeated in this phase.
* The Electron preview reads through the app's existing data-URL cap; a very large PDF falls back to **Open**.
